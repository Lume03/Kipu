# BUG-002 — Pantalla vacía después de guardar la edición de un movimiento

## Clasificación

- **Estado:** defecto visual reproducido por QA en el dispositivo, **2 reproducciones / 2 intentos**.
- **Severidad:** Media. El contenido de la aplicación queda vacío y la navegación ordinaria no recuperó la pantalla en las pruebas; se necesitó cerrar el proceso y relanzar.
- **Prioridad:** P2. Hay recuperación por relanzamiento y no se demostró pérdida del movimiento; no se presenta como corrupción ni crash.
- **Alcance:** HU-20, Sprint 4, edición de movimientos / navegación. Funcionalidad dentro de S1–S6.

## Entorno y límites

- Kipu Android, paquete `com.kipu.app`, versión `0.1.0`, `versionCode=1`.
- Samsung SM-A165M, Android 16 / API 36; sesión ya iniciada y datos identificables `QA_`.
- Auditoría iniciada el 2026-10-19 y continuada el 2026-10-20.
- El acceso Premium QA local informado para esta instalación no demuestra una suscripción comercial ni derechos remotos.
- **No se pudo vincular el APK instalado al commit ni al incremento del Sprint 6.** Las referencias de código siguientes son contexto estático, no prueba de causa en el binario.

## Precondiciones

Un gasto creado exclusivamente para la auditoría y consultable desde Movimientos. No usar un movimiento personal ni editar datos preexistentes ajenos a los fixtures.

## Pasos de reproducción ejecutados

1. Abrir Movimientos y seleccionar un movimiento de prueba `QA_...`.
2. Elegir **Editar**.
3. Cambiar un campo por un valor válido y pulsar **Guardar**.
4. Observar el área de contenido después de cerrarse el editor.
5. Intentar recuperar la vista mediante navegación normal a otra pestaña.
6. Cerrar el proceso y relanzar la app; volver a Movimientos.
7. Repetir con un segundo movimiento QA distinto.

## Resultado esperado y fundamento

Una edición válida debe devolver a una lista/detalle visible con el registro actualizado y mantener utilizable la navegación. Es el flujo de edición de HU-20 y no debe exigir reiniciar el proceso para seguir usando la app.

## Resultado observado

En ambos intentos de QA, después de guardar el área de contenido quedó vacía. Cambiar de pestaña no recuperó el contenido durante la prueba. El cierre del proceso y relanzamiento restauraron la app, y el movimiento editado volvió a aparecer en Movimientos.

La captura adjunta documenta el contenido vacío antes de relanzar; **no demuestra por sí sola los dos intentos, el guardado en almacenamiento o una causa técnica**. La frecuencia y la recuperación proceden del registro de ejecución de QA.

## Impacto funcional y financiero comprobado

- Bloqueo temporal de la interfaz tras un flujo esencial de edición.
- No se demostró pérdida de movimientos, duplicación de importes ni alteración financiera provocada por la pantalla vacía.
- Persistencia/sincronización remota no confirmadas.
- En el recorte consultado de logcat no se detectó `FATAL EXCEPTION` atribuible al paquete; esto no descarta errores fuera del recorte ni identifica causa.

## Investigación técnica — hipótesis, no causa confirmada

En el checkout `dd6758a01a236aa61053ebf8ab24f25e0c835ba5`, el éxito de edición emite `TransactionRevised` y después `CloseEditor` (`MovementEditorViewModel.kt:359–364`); el collector invoca `onSaved` y `onDismiss` (`MovementEditorSheet.kt:107–113`), cuyos callbacks solicitan `popBackStack()` (`MovementsNavigation.kt:96–100`). Un posible retorno adicional debe contrastarse con el lifecycle/stack y la reproducción; no se afirma que sea la causa del APK probado.

No se modificó código ni se compiló/reinstaló para comprobar esa hipótesis.

## Workaround observado

Cerrar el proceso y relanzar la app; abrir Movimientos. No borrar datos, reinstalar, manipular DB ni volver a guardar repetidamente para recuperar la vista.

## Verificación recomendada para una corrección posterior

- Editar y guardar dos movimientos QA independientes; la lista/detalle debe renderizarse tras cada guardado.
- Confirmar que el cierre del editor ocurre una sola vez y mantiene un destino válido.
- Cubrir Atrás, navegación entre pestañas y reapertura.
- Verificar que los cambios persisten sin duplicar movimientos ni efectos financieros.
- Correlacionar tracing de eventos/destinos con el síntoma antes de atribuir una causa.
