## 3. Recomendaciones técnicas y decisiones de producto aprobadas (pendientes de revisión arquitectónica)

1. **Estado de negocio**: Producto aprobó estado explícito `ACTIVE` / `PAUSED` / `CANCELLED`, separado del tombstone `deleted_at`. `is_active` es proyección read-only: `ACTIVE=true`; `PAUSED`/`CANCELLED=false`. Retener hasta que un inventario autorizado confirme que no quedan lectores legacy; retirarlo solo mediante una migración posterior revisada. El inventario no se ha realizado y no se infieren lectores/escritores legacy. `CANCELLED` terminal y la reutilización mediante una regla nueva también quedaron aprobadas.
2. **Versionado remoto**: usar una migración SQL incremental, forward-only y no destructiva. No copiar/reaplicar el baseline local ignorado ni recrear tablas. Antes de ejecutar una migración vinculada, verificar el catálogo/estado remoto autorizado; si se desconoce, detener el despliegue, no adivinar.
3. **Comandos/sync**: seguir el patrón probado en metas: ID de operación estable, hash de solicitud, versión de contrato y revisión esperada; operaciones repetidas idénticas devuelven el recibo anterior, el mismo ID con contenido distinto produce conflicto y revisión obsoleta no sobrescribe el estado. Room persiste cambio local y outbox en una transacción; no se produce efecto financiero.
4. **Fecha**: mantener cálculo puro y determinista por fecha de calendario; mensual/anual se anclan a la regla y se ajustan al último día válido, no a la hora incidental de ejecución. Al reanudar, mostrar la primera fecha futura válida; solo después de confirmación explícita se persiste `ACTIVE`, sin generar gastos por periodos omitidos.
5. **Notificaciones**: `reminder_lead_days` es un entero requerido/no nulo; el cliente aplica default 2 antes de calcular el hash y comandos con campo omitido o `null` se rechazan. El rango es inclusivo 0–30. EP-REC conserva el valor y estado/revisión consumibles por EP-NOT; no programa ni cancela notificaciones en este slice. La semántica de entrega de 0 días permanece en EP-NOT/HU-44.
6. **Room**: el alcance requiere una migración local v22→v23, export de esquema y pruebas de preservación. No habilitar fallback destructivo.

## 6. Canonicalización numérica del comando (TECH-REC-HASH-01)

- T003 identificó que la entrada RPC se recibe como `jsonb`; por tanto, la grafía lexical original de números como `100`, `100.00` o `1e2` no es una base verificable para rechazo posterior. Este seguimiento elige el valor semántico JSONB: decimal exacto en notación base 10 sin exponente, sin ceros fraccionarios finales y con cualquier cero (incluido negativo) representado como `0`. Formas numéricas con el mismo valor producen los mismos bytes.
- La validación precede a hash acceptance, receipt lookup, idempotency o mutación. `contract_version`=1; `expected_revision`/`revision` enteros [1,9223372036854775807]; `reminder_lead_days` [0,30]; frecuencias integradas requieren `interval_count=1`; CUSTOM WEEK [1,5200], MONTH [1,1200]; `template_transaction.amount_minor` entero positivo [1,9223372036854775807], además de reglas de moneda/plantilla. Rechazar fracción, fuera de rango, tipo no numérico o path no permitido. Grafía decimal/exponencial se acepta si su valor exacto satisface campo y rango.
- El código actual observado no basta para asumir paridad: `internal.goal_canonical_json(jsonb)` en `supabase/migrations/20261017180000_ep_met_goal_schema.sql:47-63` devuelve `v::text` para escalares; `GoalCommandHasher.kt:28-40` serializa `JsonPrimitive`. EP-REC debe añadir la normalización explícita equivalente (PostgreSQL `numeric`/`trim_scale` y texto decimal; Kotlin decimal exacto, nunca `Float`/`Double`), no copiar sin adaptación esos caminos.
- Los vectores nuevos de `recurrence-command-contract.md` incluyen bytes y SHA-256 calculados documentalmente mediante Python `hashlib`. Esto comprueba los valores de referencia y sus bytes especificados solamente; no son pruebas Kotlin/SQL. T006/T010 deben reproducirlos y demostrar paridad local antes de declarar interoperabilidad. No se han ejecutado pruebas EP-REC ni se ha accedido a Supabase hosted.

## 7. Cierre de serialización, schema y calendario (TECH-REC-STRING-01 / PAYLOAD-01 / CALENDAR-01)

- **String bytes**: los valores semánticos JSONB se canonizan mediante algoritmo explícito: quote/backslash escapan; slash literal; U+0008/09/0A/0C/0D como escapes cortos; otros U+0001..001F como `\u00xx` hexadecimal lowercase; los demás escalares Unicode salen como UTF-8 literal, incluidos no-ASCII/U+2028/U+2029. Sin BOM, NFC/NFD permanecen diferentes y grafías JSON equivalentes colapsan al mismo string. U+0000 no es representable por JSONB y surrogate inválido se rechaza. Los golden string bytes/hash de contrato fueron calculados como fixtures documentales; tests Kotlin/PostgreSQL siguen pendientes.
- **Schema**: `recurrence-command-contract.md` §2 enumera campos/requeridos/nullability/allowlist de CREATE, UPDATE, SET_STATUS y `template_transaction`, incluidos refs y exclusiones; unknown keys se rechazan. En CREATE/SET_STATUS, nullable key presente con `null`; en UPDATE la omisión es “sin cambio”, null limpia solo campo nullable y `reminder_lead_days` es requerido/no nulo. El cliente materializa `interval_count=1` y lead days=2 al crear; UPDATE reenvía el lead time actual salvo cambio explícito. No hay defaults de servidor. Toda validación schema/reference/numeric/calendar precede hash acceptance, receipt lookup, idempotencia y escritura.
- **Calendario y límites**: `start_date` inmutable como ancla. Fechas estrictas gregorianas `0001-01-01`..`9999-12-31`; integradas con count 1; CUSTOM WEEK [1,5200], MONTH [1,1200]; date `next_due_date` debe pertenecer a secuencia anclada y respetar end date. Mensual/anual y CUSTOM/MONTH se derivan de la fecha original con recorte de mes sin deriva; overflow se rechaza. Estos guardrails técnicos documentales fueron aprobados por T003; la validación de implementación sigue pendiente, y no se definen nuevas cadencias de producto.

## 8. Frontera JSONB y nombres de miembro duplicados (TECH-REC-JSON-01)

- El RPC de EP-REC recibe el comando como `jsonb`, no como bytes de texto crudo. PostgreSQL documenta que `jsonb` no conserva claves duplicadas y retiene el último valor para cada nombre de miembro ([PostgreSQL 17, JSON Types §8.14](https://www.postgresql.org/docs/17/datatype-json.html)). En consecuencia, el handler no puede detectar ni rechazar lexicalmente duplicados después del parseo.
- La elección contractual conserva JSONB y define validación/hash sobre el único objeto semántico resultante. La allowlist, los tipos, required/omit/null, referencias, números, reglas calendario y validación previa a hash/recibo/mutación se aplican a ese objeto. El hash no usa el texto JSON original.
- El cliente debe construir objetos command sin miembros duplicados y serializar estructuras tipadas/mapas; no concatenar JSON manual. Las pruebas SQL deben pasar una muestra JSON con clave repetida por la conversión a `jsonb` de la interfaz y validar el valor superviviente/hash semántico, sin esperar rechazo lexical. Las pruebas Kotlin deben comprobar miembros únicos en la salida del serializador. No se han ejecutado estas pruebas ni se afirma paridad de implementación.
