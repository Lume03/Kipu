# Data Model — EP-REC (decisiones de producto y contrato documental aprobados; implementación pendiente)

## Source and compatibility

El diccionario Kipu V4.2 (`03_Kipu_V4.2_Arquitectura_y_Datos.md`, §10) define `public.recurrences` con `id`, `user_id`, `template_transaction`, `frequency`, `interval_count`, `start_date`, `end_date?`, `next_due_date`, `is_active`, `revision` y `deleted_at`. La propuesta conserva esos campos/nombres compatibles cuando sea posible y agrega los datos que HU-33/HU-35 requieren y que faltan en ese diccionario: modalidad de importe, anticipación en días y estado PAUSED/CANCELLED distinto de `is_active`.

Esto es un diseño, no una migración aplicada ni autorización hosted. El SQL bajo `supabase/local-baseline/` está ignorado/no versionado; la tabla y cualquier compatibilidad deben preflightarse contra el estado remoto antes de una aplicación hosted. DP-REC-01..06 tienen respuestas de producto registradas en T001 y el contrato/modelo documental recibió APPROVED en T003 (`t_a0fdee9b`); esto no valida implementación ni paridad runtime.

### `template_transaction` normalization and schema

- The exact nested keys are `concept` (non-empty string), `type`, `amount_minor`, `currency_code`, `source_account_id`, `destination_account_id`, `category_id`, `merchant_id`, and `merchant_provisional_text`. Reject unknown keys. All keys are required; source/destination/category/merchant IDs and provisional text are nullable but represented as explicit JSON `null` when absent. The whole nested object replaces atomically on UPDATE.
- `type` is exactly `EXPENSE`, `INCOME`, or `TRANSFER`; `amount_minor` is exact integer [1, 9223372036854775807], never float; `currency_code` is an uppercase supported code in the existing `currencies` table.
- Non-null account/category/merchant references are validated under the authenticated owner and existing eligibility rules before hash acceptance. Account currency must match. EXPENSE requires a source account and category; INCOME requires a source account; TRANSFER requires distinct source and destination accounts. Non-applicable references are null. `merchant_id` and `merchant_provisional_text` are mutually exclusive; provisional text is accepted only when no catalog merchant is set.
- The command schema is grounded in `MovementDtos.kt:19-44`, `MovementModels.kt:63-122`, and `20261002234503_s4_register_transaction_v2_hash.sql:39-64`, with recurrence-specific exclusions. `concept` is the recurring-template label from P19 §3; copying it does not write or mutate the source movement.
- `amount_mode` is stored beside the copied template, not inferred from amount presence. Preserve source movement/history. A recurrence is not a transaction/event and changes no ledger, balance, budget or movement status.
- The canonical UTF-8 command bytes are at most 16,384 bytes. Reject oversized input before hash acceptance or mutation.

## Entity: `RecurrenceCommandOutbox` (Android local-only)

| Field | Type / rule |
|---|---|
| `user_id`, `operation_id` | Composite stable operation key; operation ID is generated once and reused on every retry. |
| `recurrence_id`, `command_type` | Command target and one of the approved command names in `contracts/recurrence-command-contract.md`. |
| `request_hash`, `contract_version` | Lowercase SHA-256 of the canonical envelope, contract v1; same bytes/rules on Kotlin and PostgreSQL. |
| `expected_revision` | Required for commands updating an existing rule; absent only for create. |
| `payload` | Immutable canonical command payload. CREATE uses the complete required key set; nullable values are explicit null. UPDATE uses a non-empty patch (omission=unchanged, null=clear only for nullable fields) and always requires non-null `reminder_lead_days`; SET_STATUS has exact per-target fields. See §2 of the command contract. |
| `state`, `attempt_count`, `next_attempt_at`, `lease_until` | Retry/lease fields following the existing goals outbox pattern; no independent sync loop if existing scheduler can be reused. |
| `last_error_code`, `result_payload`, `created_at`, `updated_at` | Stable error/receipt and local retry diagnostics; do not store credentials or access tokens. |

A local state change and its outbox row must commit in one Room transaction. An identical retried command returns the original receipt; an operation ID reused with a different canonical payload conflicts; a stale expected revision does not overwrite newer state. Updating the projection/receipt is atomic locally.

## State transitions (HU-35; DP-REC-04 approved)

| From | Action | To | Requirement |
|---|---|---|---|
| ACTIVE | Pause | PAUSED | Stop future notices at the HU-44 boundary; retain rule and history. |
| PAUSED | Resume after explicit confirmation | ACTIVE | Show/recompute the first future valid date; emit/apply ACTIVE only after the person confirms it. Carry that exact date as `confirmed_next_due_date`; do not create missed transactions, expenses, payments, or occurrences. |
| ACTIVE | Cancel (confirmed) | CANCELLED | Stop future notices, preserve history. |
| PAUSED | Cancel (confirmed) | CANCELLED | Preserve history; cancellation is terminal per approved DP-REC-04. |
| Any | Leave cancel confirmation | unchanged | FR-009. |
| CANCELLED | Any state transition | not allowed | Terminal per approved DP-REC-04. Clone/create a new recurrence to reuse its configuration. |

Every applied state transition increments `revision`. A repeated pause/cancel must not duplicate history or silently restore the prior state. On revision conflict, keep pending local intent visible and let the user reload/resolve.

## Calendar and validation invariants

- Calendar range is strict Gregorian `0001-01-01`..`9999-12-31`, matching the shared usable range of Kotlin `LocalDate` and PostgreSQL `DATE`; reject parse errors, overflow and values outside it.
- Built-in WEEKLY, BIWEEKLY, MONTHLY, ANNUALLY use `interval_count=1`; BIWEEKLY means 14 days. CUSTOM uses WEEK or MONTH with count [1,5200] or [1,1200], respectively (maximum 100 years per custom unit). The client sends every field; there is no server default.
- `start_date` is the immutable schedule anchor. `next_due_date` must be a member of the deterministic sequence and not before the anchor; `end_date`, if present, cannot precede start or be before next due. For monthly/yearly/CUSTOM-MONTH, derive each candidate from the original anchor's year/month/day and clamp to the target month's last valid day; do not advance from a previously clamped date, so a January-31 series returns to the 31st in March. WEEKLY/CUSTOM-WEEK add whole weeks from the anchor; BIWEEKLY adds 14-day multiples. No timer execution timestamp changes the anchor.
- Any cadence edit requires the complete `frequency`, `interval_count`, `custom_interval_unit` tuple and a valid replacement `next_due_date`; invalid/overflowing/out-of-range results reject. Do not saturate to `9999-12-31`.
- `end_date` is optional in S6; if present it must be on/after `start_date` (approved DP-REC-03).
- Resume must show/recalculate the first future valid next date; only after explicit confirmation may the client emit ACTIVE with that exact date as `confirmed_next_due_date`, which the server validates against the first future valid date (approved DP-REC-02). Never materialize missed periods as expense, payment, transaction, or `recurrence_occurrences` rows.
- `reminder_lead_days` is an integer NOT NULL in the model and required in CREATE and every configuration UPDATE, range 0–30. The client inserts default 2 on CREATE; UPDATE re-sends the stored value unless the person changes it. Missing/`null` commands are rejected. EP-NOT/HU-44 owns delivery meaning for 0.
- Calendar functions are pure/deterministic. Repeating the same calculation from the same anchor and input yields the same due date.

## Canonical JSON values (TECH-REC-HASH-01 / TECH-REC-STRING-01)

The command hash is over semantic JSONB values; original numeric token spelling is not retained by the RPC boundary and must not be validated lexically after parsing. Normalize every admitted JSON number as an exact base-10 decimal with no exponent, remove trailing fractional zeroes and a now-empty decimal point, and serialize all zero values as `0`. Thus `100`, `100.00`, and `1e2` have identical canonical bytes; `1e-1` canonicalizes to `0.1`. Kotlin must use exact decimal/integer arithmetic and PostgreSQL must normalize its exact `numeric` value (for example `trim_scale(numeric)::text`); neither side may pass through binary float/double.

The same JSONB boundary applies to object member names: PostgreSQL removes duplicate names during JSONB parsing and keeps the last value. RPC validation cannot reject the original lexical duplicate and MUST validate/hash only the resulting semantic object. The client MUST emit command objects with unique member names; SQL tests exercise the post-parse `jsonb` value and Kotlin tests check duplicate-free command serialization. Unknown keys and all other schema/business validations remain mandatory before hash acceptance, receipt lookup or mutation.

Before hash acceptance, receipt lookup, idempotency processing or persistence, validate every allowlisted number as an exact mathematical integer and against its range: `contract_version=1`; `expected_revision` and stored `revision` [1, 9223372036854775807]; `reminder_lead_days` [0,30]; built-in `interval_count=1`; CUSTOM WEEK count [1,5200] or MONTH count [1,1200]; `template_transaction.amount_minor` [1,9223372036854775807]. A decimal/exponent spelling whose exact value is an in-range integer is accepted as that integer; fractions, out-of-range values, non-number types and unallowlisted numeric paths reject. `amount_minor` also follows currency/template validation. These technical constraints create no financial effect and do not expand the HU-33/HU-35 field allowlist.

String bytes follow TECH-REC-STRING-01 in the command contract: exact JSON string quoting/escaping, UTF-8 for all unescaped Unicode, no normalization/BOM, equivalent JSON escape spellings map to the same scalar value, and U+0000/unpaired surrogates reject. Do not assume Kotlin or PostgreSQL default serializers agree; parity tests are required before implementation compatibility can be claimed.

## Relationships and excluded entity

- `auth.users 1:N recurrences`; all remote reads/writes are owner-scoped.
- A recurrence is initialized from an existing movement's detail/template; source history remains immutable. The specification does not require an FK from the recurrence to the source transaction; do not add one without approval.
- `recurrence_occurrences` is documented by V4.2 for HU-34/HU-44/HU-46/HU-51 but is **not read/written/generated** by this epic. No occurrence generator, matcher, or transaction-creation path is included.
